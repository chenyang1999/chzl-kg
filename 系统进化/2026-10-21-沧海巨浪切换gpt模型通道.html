  • 日期：2026-10-21，时区 Asia/Shanghai。
  • 用户说明字节 Agent Plan 用量耗尽，已将当前桌面聊天切到 GPT，要求检查后台是否一起配置。
  • 已展示迁移差异：默认及独立 Agent 配置改为 openai-codex / gpt-6.1-sol，清除旧厂商地址覆盖；15 个大模型定时任务同步切换；保留字节配置用于回退，不改调度、交易规则或数据源。

三、逐项真相与可核验证据

1. 桌面聊天切模型不等于后台切模型

迁移前，default 保存的是 minimax-cn / MiniMax-M3.1-Flash，当前聊天通过会话覆盖使用 GPT。四个现存 canghai 独立配置仍是 volcengine-coding-plan / ark-code-latest。

全量读取 default 与四个 canghai 定时任务库，共 37 个任务：15 个大模型任务、22 个脚本任务。15 个大模型任务原来全部固定使用 volcengine-agent-plan / deepseek-v4-flash-ga-260731。

2. 早盘研究入口必须连独立配置一起迁移

~/.hermes/scripts/canghai_research_daily.sh 调用项目内编排脚本。scripts/research/run_research_shell.sh:82 通过 hermes -p canghai-research chat 启动研究步骤，因此外层定时任务虽然是脚本，内部仍使用研究 Agent 的模型。仅切换定时任务字段无法覆盖这条路径。

3. 先试单点，再批量切换

迁移前以研究 Agent 做了一次 GPT 显式覆盖测试，终端返回 GPT_MIGRATION_CANARY_OK，退出码 0。

批量迁移后，逐个在不指定 --provider、--model、--base-url 的情况下启动 5 个独立会话，要求只执行 printf 并返回唯一标识。全部退出码 0；日志确认每次至少完成一次真实 terminal 工具调用，而不是只回复标识文本。

4. 逐条核验定时任务入口

使用 Hermes 自身解释器，在任务所属目录的运行作用域中调用 resolve_runtime_provider。15 个任务均解析为：

  • provider：openai-codex
  • model：任务保存值 gpt-6.1-sol
  • api_mode：codex_responses
  • base_url：https://chatgpt.com/backend-api/codex
  • 凭据：可解析；未显示、复制或修改登录令牌。

这证明配置和登录入口有效，不代表已经重跑15个生产任务，也不代表完整研究质量、并发容量或竞价时限已验收。

9 个脚本任务仍有历史字节模型字段，但 no_agent=true 本身不调用推理层。不要把这些标签误报成仍有 9 个大模型任务漏切。若脚本内部另起 Agent，以其实际启动命令和独立配置为准。

五、根因与执行注意事项

  • 主聊天会话覆盖、保存的默认配置、独立 Agent 配置、每个定时任务固定模型是不同入口，不能只改一层。
  • 使用官方 hermes -p <name> config set 与 hermes -p <name> cron edit 修改，而非复用旧的字节套餐切换脚本。
  • 当前 CLI 在设置 model.provider 时会清除旧 model.base_url。第一次无条件执行 unset 因字段已被清除而返回「Config key not set」，批次停止；立即回读确认只有已授权字段改变，随后改为仅在字段仍存在时 unset，幂等重跑完成迁移。没有绕过错误继续假报成功。
  • 所有配置均与备份作语义比对，除 model.provider/default/base_url 外保持一致。
  • 未重启或终止正在运行的任务；新会话测试已读取新配置，旧会话不强制热切。

六、改进建议

  1. 优先观察下一次完整生产运行：配置和最小工具调用已通过，但整条研究流水线耗时、质量、并发用量与竞价窗口仍需由真实生产运行验收，不应为验证而覆盖当日产物。
  2. 当前固定到 GPT 的任务不会因为主聊天临时切模型而跟着漂移。未来切回字节时，同样需要同时处理独立配置与任务固定模型。
  3. scripts/cron/switch_cron_provider.py 是旧字节方案专用脚本，硬编码字节模型与端点；本次未运行或改造。不要把它当通用 GPT 切换器。
  4. GPT 通道也有自己的用量与并发限制；本次最小测试未测定可用余额或满负载容量，不宣称额度无限。
