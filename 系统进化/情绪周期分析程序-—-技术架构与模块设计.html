一、架构总览

1.1 设计原则

  1. 单机优先：用户本地运行，不引入数据库、消息队列等重型依赖。

  2. 层间解耦：标签引擎必须是纯函数，不得依赖数据源或外部状态。

  3. 可测试优先：核心判定逻辑（标签引擎）必须能在无网络、无 Tushare 的环境下被单元测试覆盖。

  4. 渐进降级：Tushare 不可用、积分不足、历史数据缺失时，程序不崩溃，自动降级并显式提示。

二、技术选型与 ADR

ADR-001：核心语言与数据处理栈

状态： Accepted

决策： Python 3.10+ + pandas + numpy

理由：

  • 需求已确认为 Python 命令行 + 网页；pandas 是 A 股量化分析的事实标准；numpy 处理数值运算。

  • 备选：Rust/Go 性能更好，但量化生态（Tushare、pandas、matplotlib）绑定 Python，切换成本不划算。

  • 备选：Polars 比 pandas 快，但团队熟悉度低、Tushare 返回 pandas DataFrame 原生兼容，暂不引入。

ADR-002：网页层选型 — Streamlit

状态： Accepted

决策： Streamlit（而非 FastAPI + 前端框架）

理由：

维度StreamlitFastAPI + React/Vue
本地启动streamlit run web.py 一行搞定需同时启前后端两个服务
开发成本Python 写界面，无前端代码需写 REST API + 前端组件
数据展示原生支持 DataFrame、图表、指标卡片需前端图表库 + 接口对接
定制性中等，布局受限高，可任意定制
部署复杂度极低中等

取舍： 本期网页只做展示、无交互改规则、无用户登录。Streamlit 的「单命令启动 + 纯 Python 开发」完美匹配「用户本地运行简单」的硬性约束。若未来需要复杂交互或多人部署，再迁移至 FastAPI + 前端框架。

ADR-003：图表库 — Plotly

状态： Accepted

决策： Plotly（而非 matplotlib）

理由：

  • Plotly 输出交互式 HTML，可直接嵌入 Streamlit 页面；matplotlib 静态图在网页中体验差。

  • Streamlit 原生 st.plotly_chart() 支持。

  • CLI 场景下 Plotly 也可导出静态 PNG，两用。

ADR-004：本地缓存格式 — JSON Lines

状态： Accepted

决策： 按交易日存储为 .json 文件（JSON Lines 用于批量序列）

理由：

  • 人可读、可手动检查；Python 原生支持；比 CSV 更适合嵌套结构（如涨停明细列表）。

  • 比 SQLite 轻量，不引入数据库依赖，符合单机优先原则。

  • 增量更新天然支持：检查文件存在性即可。

三、模块详细设计

3.1 配置层（config/manager.py）

职责： 统一管理 Tushare token、缓存路径、指数代码等配置。

配置加载优先级（高 → 低）：

  1. 环境变量：EMOTION_TUSHARE_TOKEN、EMOTION_CACHE_DIR 等

  2. 用户配置文件：~/.emotion_cycle/config.yaml

  3. 项目内默认配置：config.yaml

ConfigManager 接口：

待确认项： 配置文件的 YAML 结构是否需支持多环境（dev/test/prod）？当前按单环境设计。

3.2 数据层（data/）

3.2.1 Tushare 客户端（tushare_client.py）

职责： 封装 Tushare Pro API，处理降级、限流、网络失败。

3.2.2 本地缓存（local_cache.py）

缓存目录结构：

~/.emotion_cycle/cache/
├── 2026/
│   ├── 20260901/
│   │   ├── limit_list.json
│   │   ├── daily.json
│   │   ├── stk_limit.json
│   │   └── index_daily.json
│   ├── 20260902/
│   └── ...
├── 2025/
└── ...

缓存策略：

  • 写入： 每次 Tushare 拉取成功后立即写入对应日期目录。

  • 读取： 优先读本地缓存；缓存不存在才调 Tushare。

  • 增量更新： 历史回放时，遍历日期范围，逐日检查 os.path.exists()，缺失日自动拉取。

  • 缓存元数据： 每个 .json 文件内嵌 "_source": "tushare" 或 "_source": "daily_rebuild"，用于追溯。

3.2.3 离线样例数据（offline_demo.py）

职责： 无 token 时提供内置 30 日模拟数据，覆盖五档标签完整循环。

样例数据来源： 从复盘文档 2019–2026 标签分布中抽取真实交易日的指标特征，脱敏后构造模拟数据。

3.2.4 数据降级策略

场景降级路径输出标注
limit_list_d 返回为空（2019 年或积分不足）用 daily + stk_limit 重建涨停/炸板/跌停名单data_quality: "降级(daily重建)"
daily 也失败尝试本地缓存旧数据data_quality: "降级(缓存)"
完全无数据跳过该日，历史回放中留空；日度分析报错提示—
无 token进入离线演示模式data_quality: "离线演示"

2019 年重建逻辑（daily + stk_limit）：

重建数据限制（需在输出中显式提示）：

  • 封单金额、首次封单时间缺失；

  • 连板数为估计值，可能偏低；

  • 炸板率计算可能偏低（因部分炸板特征无法从日线还原）。

3.3 指标计算层（core/indicators.py）

职责： 从原始数据计算 8 项指标，输出结构化对象。

计算依赖：

  • 单日指标需要当日 limit_list_d + index_daily + 近 10 日历史指标（用于 10 日峰值）。

  • 历史回放时，按日期顺序逐日计算，缓存近 10 日结果供后续日使用。

补跌任意空尽量不碰情绪票当超跌反弹满仓

六、风险与降级路径

6.1 Tushare 接口积分不足

风险等级高
触发条件用户 token 积分 < 120，limit_list_d 调用被拒
降级路径1. 提示积分不足；2. 自动尝试 daily + stk_limit 重建；3. 仍失败则进入离线演示模式
输出标注data_quality: "降级(积分不足，daily重建)" 或 data_quality: "离线演示"
用户动作充值 Tushare 积分 或 接受降级数据

6.2 2019 年数据缺失

风险等级中
触发条件日期 < 2020-01-01，limit_list_d 返回为空
降级路径自动使用 daily + stk_limit 重建涨停/炸板/跌停名单
输出标注data_quality: "降级(daily重建)"，并在 CLI / 网页显式提示重建限制
已知限制封单金额缺失、连板数估计、炸板率可能偏低

6.3 网络失败 / Tushare 服务不可用

风险等级中
触发条件请求超时、连接失败、Tushare 服务端返回错误
降级路径1. 重试 2 次（间隔 3 秒）；2. 尝试本地缓存；3. 无缓存则报错并提示检查网络
输出标注使用缓存时 data_quality: "降级(缓存)"，标注缓存日期

6.4 极端行情指标失真

风险等级中
触发条件千股跌停、全场普涨等极端日，常规指标边界模糊
降级路径标签引擎输出 confidence: "低"，并附加 transition_warning 提示人工复核
输出标注CLI 用黄色/红色高亮低置信度日；网页用警示卡片

6.5 总龙识别简化偏差

风险等级低
触发条件程序简化版总龙识别（前 N 日高标 + 换手）与市场实际总龙不一致
降级路径总龙开关仅作为「温度参考」，不纳入标签引擎硬性判定条件
输出标注总龙状态旁标注「简化识别，仅供参考」

七、待确认项（需主 AD / 产品经理确认）

  1. 配置多环境支持： 当前按单环境设计。是否需要支持 dev / test / prod 多配置文件？

  2. 历史对照测试数据来源： 验收测试 2/3 中的「复盘文档基准标签」是否有结构化数据文件（如 Excel / CSV）可供程序直接读取对比？当前设计假设通过 playback 输出后人工或半自动对比。

  3. 离线样例数据构造方式： 内置 30 日样例数据是否从真实历史脱敏构造，还是完全模拟生成？前者需要获取一段真实数据授权。

  4. Streamlit 端口冲突： 默认 8501 端口被占用时的行为？当前设计：自动尝试 8501+1，或用户通过 --port 指定。

  5. 标签引擎阈值参数： 五档标签的具体数值阈值（如「炸板率 > 多少算高」）当前按复盘文档定性描述设计，是否需要产品经理提供具体量化阈值？
