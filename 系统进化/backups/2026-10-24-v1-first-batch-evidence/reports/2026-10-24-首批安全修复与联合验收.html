1. 授权与要求

用户要求：先保守清理无用的零散/临时文件，修复前 Git 提交一版，再分多个 Agent 实施修复。

本次按三个互斥文件组实施，再增加最终权限接线、独立审查、同一源码联合验收及有限收尾。所有者交接后才允许下一写者修改共享文件，不并行覆盖生产源码。收尾涉及测试契约迁移，均保留旧失败、改前原件与裁决，不能靠放松生产门禁获得通过。

不在本次授权内：改模型、永久定时任务、SOUL、技能语义、账户配置、风险阈值、生产输出路径；整删网站或历史数据；重跑生产；恢复实盘。

本次判定标准

  • 权限只能收紧，不能由命令行参数、账户默认值、已有持仓或缺字段补授。
  • 正式零预算必须保持零；买入门禁不应无故阻断已有明确规则的合法退出。
  • 缺扫描、未突破、无有效盘口、未知可卖量不能下单。
  • 比例止盈不能占住剩余仓位，导致后续保护退出失效。
  • 装载与执行分离，每轮只分派一次。
  • 同一份最新源码上验证正常买入、合法退出、拒绝、重启及重复输入，不以各组历史通过数相加。

3. 逐项修复与证据

3.1 账户风险配置不能扩大正式计划

  • 四个既有买入上限取明确值的交集；计划预算缺失不由账户正值补齐，正式零预算不被扩大。
  • 禁区取并集，风险警示限制不被账户覆盖；未知风险字段、异常类型或冲突的停机路径显式拒绝。
  • 单票预算缺失不再被模型的正数默认值解释成花钱许可。
  • 入口与最终买入边界均验证预算；正数预算使用现有字段及模式隔离日志进行保守占用检查，不另选阈值。

位置：trading/execution_authorization.py:22、:51、:80；trading/load_plan.py；trading/order/qmt_context.py:234、:310。

3.2 live 参数不等于授权

  • 计划、账户与逐票许可分别核对；运行参数只能请求执行模式，不能补自主交易或绕过人工确认。
  • 已有持仓不再自动打开该票的买入许可。
  • 装载和 watcher 把计划/账户快照绑定到最终订单上下文；最终边界重验日期、模式、预算、执行池、逐票权限、选定规则、拟限价盈亏比及扫描证据。
  • 未绑定或无效上下文在订单客户端调用前拒绝。
  • 持仓观察票仅在有明确退出规则时投影为只退出，不升级买入资格。

位置：trading/execution_authorization.py:86、:109；trading/load_plan.py:344；trading/watcher/run_once.py；trading/order/qmt_context.py:234。

声明限定：这里证明的是共同许可、名单、买入条件和额度检查，不能把退出 type 名单说成完整的精确卖出意图授权，见第 7 节。

3.3 每轮只执行一次

  • run_load_plan(dispatch=False) 仅准备，不构造交易上下文、不读持仓、不重置状态、不分派。
  • 默认装载执行 API 保留一次分派兼容；后台循环采用准备后 watcher 唯一分派。
  • 同日装载保留做 T 状态，不再每轮清零。
  • 真实隔离后台循环两轮由修前 4 次分派变为修后 2 次；不是只统计 mock 调用。

位置：trading/load_plan.py:344；trading/watcher/run_once.py；src/execute/watcher_daemon.py。

3.4 比例止盈不阻断保护退出

  • 比例档首次确定整数目标量并持久化；订单是否完成与剩余持仓分开，不对余仓重复乘比例。
  • 档位依真实成交历史的持仓生命周期及数值规则识别，不因新观察、日期、计划哈希或说明文字重置。
  • 每轮先评估高优先级保护退出；旧止盈 pending/partial 不再整票占位。
  • 接管旧低优先级单与现金、批次、成交、流动性消耗处于同一事务；失败回滚。
  • 重启、跨日续单、同档不重复卖、旧实现真实写出的历史订单兼容均有隔离实证；缺历史规则证据时拒绝比例重试，不凭空改账。

位置：trading/paper/ledger.py:568 起的生命周期/目标恢复，:678 的执行边界；scripts/execute/run_paper_plan_once.py。

3.5 模拟账本低层复查停机文件

  • 低层账本执行自行核对既有默认停机文件及批准路径，不信计划自填 false。
  • 只检查文件存在性，不读取内容；路径不明、符号链接或未知状态拒绝新买。
  • 合法存量退出与买入预算、研究资格及买入停机门禁分离。

位置：trading/paper/safety.py:10；trading/paper/ledger.py:678。

3.6 扫描、突破、定量与盘口

  • 缺扫描、抓取失败、扫描异常、重复/冲突信号拒买；重算时替换旧证据，不能沿用旧成功。
  • 独立审查发现原扫描日期只保存未消费，默认 loader API 可复用异日成功扫描；已补为计划/context/scan 日期一致，缺日期同样拒买，不补“今天”，不暗设报价年龄阈值。
  • 突破必须达到有效 trigger 及显式确认/收复价，ask 满足已有上限；复杂未实现谓词明确不支持。
  • 数量按目标股票与拟提交限价计算，并受现金和单票剩余预算约束；买不起一手返回零，不再强行至少买一手。
  • 可卖量未知/非法不回退总持仓；零保持零。持仓 last 不再被伪造成 bid/ask。
  • 最终卖出限价绑定已有有效 bid，不能由低层调用随意改价。

位置：trading/entry_selector.py；trading/watcher/session_context.py:62；trading/executors/base.py:154；trading/executors/_buy_common.py；trading/order/qmt_context.py:376。

5. 根因

  1. 授权散落且默认值有执行含义：模型默认、账户合并、模式参数、持仓回填各自可能扩大许可，入口检查也不能替代最终订单边界。
  2. 装载隐含执行副作用：后台以为只是刷新计划，却已分派一遍，随后 watcher 再执行；同日状态也被反复初始化。
  3. 订单目标与持仓混淆：比例卖单按剩余持仓判未完成，旧订单占票，保护退出不能独立重新评估。
  4. 证据缺失被当作兼容条件：无扫描默认放行、跨日证据不核、未知可卖量猜总仓、报价缺失从 last 回填；看似“可用”，实则失去证据约束。
  5. 测试夹具停留在旧合同：未知规则、无日期、无现金/扫描、强制至少一手曾可通过；安全修正后必须独立裁决迁移，不能把所有失败都算新生产 bug，也不能改期待掩盖真漏洞。

6. 后续建议与优先级

推荐下一批优先做研究按时交付及汇聚，而不是恢复旧交易网站。 用户最直接的问题是“每天该有的研究是否生成、是否进入预案”；这一批安全修复不能替代该闭环。
