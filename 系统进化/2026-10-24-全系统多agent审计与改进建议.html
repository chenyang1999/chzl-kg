一、授权、方法与适用边界

用户要求：“帮我深入地分析一下整体系统，给我一份详细的研报及其改进措施建议，哪些是冗余的可以去掉，哪些是核心的需要加强，分多个 Agent 详细分析。”

本次按七个独立审查方向展开：A 架构与冗余、B 调度与运行、C 研究与决策、D 执行安全与独立模拟、E 数据与证据、F 复盘回测与学习、G 界面与知识规则。它们是本次审查分工，不是新建生产角色，也没有冒充其他角色改写生产产物。

另由 H 对八个关键主题做独立交叉复核。它纠正了“模拟账没有复盘读者”和“当前保活脚本在进程存活时仍额外执行”的概括，并收窄竞价时间、代码量及规则冲突的表述。主控也独立重跑了关键测试；不是把子审查自报直接拼成结论。

审查对象是当前实际工作树、已注册调度与外部启动脚本、真实研究/预案/复盘文件及隔离测试，不是只读设计蓝图。基线分支为 main，HEAD 为 03c1d25caf94e8c8576765442b55cbf4538559f1；已有 32 项暂存、143 项未暂存、6491 条未跟踪路径。这个数字是 Git 路径统计，不能直接当作垃圾文件数量。

**审计限制：**未下单，未启动生产服务，未补跑研究，未修改业务代码、配置、任务、技能、身份文件或交易规则，未删除组件，未提交 Git；未打开真实持仓/成本/成交数据库或凭据。测试使用合成行情、合成日历及独立临时账本。活跃系统没有停机，因此不是全系统事务一致性冻结；截止后验证与观察另列。

七份分报告共有 68 条原始发现记录，包含重复观察、优化建议、正常保护和待核实项，不是 68 个独立 bug。为落实责任，整合为 18 个工作包；工作包也不是“独立根因数”。原始报告、合并映射、逐项证据、原生测试结果及主控复验记录随附件交付。

二、总体判断：不是“智能体太多”，而是边界没有闭合

这个系统已经有值得保留的东西：研究与决策分离、独立反证、正式预案与执行投影分离、单票买入资格判定、独立模拟账本、显式降级、逐票盈亏比隔离、零预算保护。10 月 22—23 日的报告也比旧版本诚实：缺证写缺证、不可评分写未知，不再把每个产物都包装成全流程成功。

但这些局部正确还没有组成稳定闭环。最主要的矛盾不是“会不会分析”，而是：

  1. 按时跑起来，未必按时交付可用结果。 现存五日竞价快照与校准版本均不能证明满足关键截止；五份校准明确超时保护。
  2. 文件已交付，未必研究已完成。 安全临时版可正确禁买，但没有可靠的后续重评触发。
  3. 有安全模块，未必所有入口都经过它。 旧执行入口、低层模拟入口、账户风险覆盖仍有边界漏洞。
  4. 已有模拟账本，未必已部署成连续运行的模拟系统。 单次正向验收和复盘读到快照是真的，常驻接线仍未证实。
  5. 有复盘和命中率，未必能评价决策价值。 事后补标签、窗口覆盖不足、实验写生产与不可成交假设仍污染旧评价路径。
  6. 页面有绿色状态，未必代表真实健康或交易许可。 部分页面把配置、实现状态、入池和可执行混在一起。

因此，本报告不支持“换一个框架就好”“删一半 Agent 就好”“放松风控就能恢复”的结论。应减少的是重复写者、权限旁路、重复事实、冲突规则和不可验证指标；不应减少的是研究覆盖、反证独立性、数据备援与审计证据。

4.2 竞价窗口为什么被挤压

五日快照任务实际触发较计划晚约 47—57 秒，整个 Agent 任务耗时约 47—63 秒；校准任务耗时约 78—240 秒。前者不是纯 API 耗时。现有链把任务唤醒、大模型取工具、抓数、判断都压进硬截止，超时保护本身没有错，交付路径尚未满足窗口；也不能把校准超时的原因全部归给快照迟交。[B01/H07]

**建议：**保留 09:27 数据形成下界，不提前抓尚未形成的数据；采集与基础三档对照改为确定性执行，快照提交后触发校准，预先准备当日计划版本。大模型保留异常判断职责，不再承担必须秒级完成的文件搬运和固定比较。超窗仍不追补成有效交易指令。具体调度实现需审批、测量，不把改一个 cron 分钟当作解决问题。

4.3 常驻任务目前与独立模拟不一致

旧常驻监控五日 1823 条记录仍写入 20260930 分区，源码只在启动时计算交易日；10/24 周六也有后续运行记录。入口仍传 dry_run，只记意图，不能当成独立模拟成交。[B03]

**交叉复核撤回一项部署断言：**仓库内同名保活脚本在进程存活时确实会另跑一次，但当前已注册任务解析到 ~/.hermes/scripts/ 中的另一版本，存活时直接退出。因此不把“保活额外轮次”记为当前部署事实。daemon 内装载与执行两次分派的问题仍独立成立。[H06]

独立模拟单次入口确实存在、经过隔离验收，10/23 日复盘也确实读过模拟账快照。**但这两件事不证明常驻部署已接到新账本。**应先认证唯一常驻服务的交易日更新、休市守卫、重启恢复、计划版本和退出管理，再决定停旧入口。[D11/F08]

4.4 推送是“责任冲突”，不只是通道偶发失灵

任务文本要求自行发送，调度统一提示又要求不要自行发送、由系统自动交付，而实际目标为本地。10/22—23 四份输出未见发送调用，交付记录为 suppressed。[B04]

整改方向是单一投递负责人，生成、投递确认、终端已读分别记账。失败入待发送队列还不够，必须有队列消费者、幂等键和确认收据。旧的某次端到端测试成功只能证明当时通道可用，不能替代本周连续交付证据。

5.2 目标执行结构

保留一个订单授权边界和一套明确的状态转换。正式计划只表达研究结论和已批准范围，账户设置只能进一步约束。装载只准备，执行只在唯一循环触发。订单至少区分意图、提交、确认、部分成交、成交、撤销；账本按成交而非文本自报更新。

独立模拟与真实账户保持环境、授权、资金、批次、成交和绩效隔离。可以复用纯校验函数和接口，不可把两个账本“合并简化”。持仓保护的输入来自有效退出规则与同一账本，不能随着执行池清空而失联。

6.2 研究完成、判断把握、交易许可分开

10/23 恢复版的研究汇总为 partial，计划 production_ready=false、research_completion_passed=false、reassessment_required=true。这可以同时满足“安全交付”和“不具备交易条件”。不应通过把标志改成完成、补一个默认信心、清空研究池来解决。

建议建立独立状态轴：交付是否成功、研究覆盖/证据质量、判断是否明确、当日交易许可。confidence=0.245 等降级系数乘积不是校准后的盈利概率。零值与缺失都不能自动回退为默认正仓位。[B02/C02/C03]

6.3 原文与母源证据的实际缺口

10/23 公告窗口有 2672 条、1050 家公司，但这是索引，不是全文。抽查五份 primary documents，完整抓取时间/正文哈希/归档指针覆盖 0/5；这证明可复现性不足，不证明研究者从未阅读原文。四条高等级事件中仅一条自报原始 URL 已核验，URL 核验又不等于全文证据闭合。[E02]

当前报告已经部分纠正“多平台转载=独立确认”的旧做法；仍应按原发布主体、母文、上游数据集和正文指纹分簇。相同东财数据经不同工具返回，只增加传输备援，不增加独立证据票数。[E03]

6.4 最小数据契约

建议沿用现有结构、增加共享适配与校验，不另造一套平行研究系统：

  • **是什么：**标的、字段、原单位、标准单位、转换方式、口径版本。
  • **谁提供：**传输工具、上游数据集、原始发布主体、母文编号、转载链。
  • **何时成立：**公告/观测时间、请求起止、抓取时间、生成时间、目标交易日、实际数据归属日、时区和精度。
  • **覆盖多少：**请求对象、返回条数、去重条数、供应商总数、是否还有下一页、有效/缺失样本。
  • **为什么缺：**错误、有效空、未调用、已退役、部分覆盖、语义无效分别表达；未知不写零。
  • **谁需要：**研究必需、执行必需、可选补充分别标记，不把可选来源的缺口升级成全系统停研究。

具体问题包括固定第一页的业绩抓取、主营缺会计期间、父子行业混算、采集时间冒充原始行情时间，以及备用计算链把 None 累加为 0。应先补这些可测试契约，再决定换供应商。[E04—E08]

**低吸语义也必须验收：**技术回踩价、低于昨收或 MA50 不能自动等于“预判当天涨停的强势低吸”。右侧、板块合力、辨识度及流通市值要求应有可核验证据，而非只有自然语言声明。[C05]

七、复盘与学习：先证明衡量正确，再证明系统在变强

7.1 最新修复必须保留

10/22 的 45 项文件检查、10/23 的 54 项文件检查都通过，但报告仍未宣称完整能力通过。10/23 生命周期报告区分了计划场景、确认入场、部分退出、完全退出；独立模拟快照也明确与真实账户分开。这些是正确改进，不能拿旧报告错误否定现状。[F01/F03/F08]

独立模拟并非“完全没人复盘”。 10/23 18:22 的日复盘证据已读取模拟账，当时订单、成交和未平批次均为零；周总结也读取过模拟快照。尚缺的是稳定的确定性只读适配、连续绩效序列、常驻执行认证及页面统一，不是从零发明读取行为。[F08；D11 采用本条修正口径]

7.2 旧评价里不能沿用的结论

  • 10/19—20 的原观察池缺少标准方向，却由日复盘事后追认兑现；这不是预先登记的预测胜率。
  • 10/21 有“零成交”和 9.29% 组合收益并存，属于旧指标混义，不应并入真实账户或独立模拟业绩。
  • 10/23 的恢复观察池在 14:22:58 形成，此前涨幅不能算系统盘前抓住的机会；14:00 参考价也早于该决策。
  • 一年窗口标记 242 个交易日、top3 命中率 82.1%，实际可评分仅 28 个、命中 23 个；候选相邻日分母 241 中覆盖 11.62%。它不是全年度胜率，更不是投资收益认证。[F01/F02/F06]

7.3 最危险的是回测污染证据

src/research/backtest_window.py:84–149 一边计算当天，一边读取本轮尚未计算的次日文件。合成三日实验首次可评分 0、重跑变 2，结果依赖磁盘先前残留。其调用计算器还可能写回正式研究目录。[F06]

建议首先隔离实验写路径，再统一先计算全部真实标签、第二遍评分的顺序；冻结预测、标签及版本，重复运行必须同结果。不要为了得到一个漂亮回测，重写当时的预测或主线文件。

旧生命周期引擎还可在入场当天模拟退出、跨日重复执行同一比例止盈、用日 K 假装知道同根柱内先后。最新报告已隔离它，但技能默认调用仍有复发入口。它与新模拟账本是不同实现，必须分别修复或退役，不能混称一个 bug。[F03]

7.4 指标内核应统一，但不能把所有收益混成一个数

指标正确用途不能替代什么
竞价买入→次日开盘/收盘价格收益用户关心的选票与持有窗口评价，分别报告不等于所有条件都可成交的净收益
次日高点/MFE事后可达上界/机会描述不能当已实际卖出的胜率
入场触发率、成交率解释从候选到实际行为的漏斗不能当策略盈利率
已平仓净收益/胜率同环境、同费用模型下的完成交易不与未平盯市、半仓退出混用
持有盯市当前模拟账户状态不等于已实现利润

预测校准与条件复发率判断与学习改进不等于错题篇数或“已采纳”次数

零成交胜率应为未知/不适用，不造 0% 或 100%；空观察池、零新仓和真实账户空仓不能互相推出。

7.5 真学习闭环的验收

纠错已有部分读者，不能再说完全没人消费；但 getter 截断到 600 字的样本中，正确逻辑在字符 727 后才开始，消费者拿不到真正的修正。还有消费者期望字段与真实观察追踪结构不同。[F07]

建议每条纠错记录 case_id、适用前提、动作、失效条件和可验证谓词，并分别记录收到、考虑、采纳、验证。按“遇到同类可比情景的次数”计算复发率，允许有理由的不采纳；禁止靠一句“已学习”宣布完成。

在数据与执行真实性稳定后，开展固定全集、固定退出和费用口径的离线消融：纠错开/关、反证增量、热度增量、画像快慢变量拆分。安全保护不得在真实或已授权模拟运行里随消融关闭。先预注册样本外评估，再选择规则，不把同窗最优当进步。

八、界面与知识：减少“看起来完成”

8.1 页面优先修四件事

  1. 显示正在看的版本。 正式研究预案、运行副本、账户装载投影应并列标来源、版本、生成/观测时点；不能无条件旧 loaded 优先。[G01]
  2. 状态不越级。 研究观察→进入计划→授权有效→实时触发→成交必须分开。执行池内有代码不能直接显示“QMT执行”。空数组回退错误已复现为有票但候选显示零。[G02]
  3. 价位缺失直说。 展示买区、确认价、最高接受价、止损/止盈、失效条件及报价时点；缺字段写名称与原因，不用 0 或“盘中确认”冒充具体价位。[G02]
  4. 健康来自证据。 当前部分健康延迟 120ms、错误率 0.01 为常量，implemented 被转为绿灯；应区分配置、连接、数据新鲜、业务交付和退役。[G03]

最新宏观 strength 别名与有效零处理已通过契约验证，应保留；剩余问题是历史回看仍可能混用最新快照、按 mtime 选到未来日期。历史页面必须只用目标时点可用的证据。[G04]

8.2 公开与私有边界

本人私有账本可以展示成本、股数、资产；公开报告默认不能含这些字段。应在服务端分公开报告、私有账户和管理写入三类接口，不能靠前端隐藏完成脱敏。设置写入需要字段白名单、差异、授权、版本校验和回读。[G06]

本轮只确认代码表面未见完整隔离及部分任意字典写入，没有核到代理鉴权，也没有证据证明已发生外泄。不能把待核验的部署边界写成既成安全事故。

8.3 技能和规则应做语义治理，不是按文件数裁剪

现有同名技能既有同字节/软链接，也有异内容副本；default 与项目共 13 组同名，其中 3 组内容分叉。部分外部目录重叠。应生成“角色→技能名→实际路径→哈希→优先层→被遮蔽副本”清单，再决定保留者。[G08]

最需要处理的是具体冲突：旧“半路禁止”与动态通道选择、置信度零回退正值、可选北向缺失却全局归零、退役数据源仍有必调配方，以及旧文中不保留关联证据的要求。最后一类不应遵从；完整可追溯性必须保留。[C03/E05/G07/G09]

“阶段约束资格/仓位”和“不固定阶段→打法”可以同时成立，不能仅因两句话并存就宣布身份契约自相矛盾。应审查具体是否强制固定动作，而不是机械做关键词冲突。

**本次没有改技能、SOUL 或记忆。**它们的修改必须先给逐项差异、等用户批准；也不能因为这份审计就清空任何角色记忆。实际注入比例、命名空间共享和 token 成本均未实测，不承诺瘦身百分比。[G10]

十、最小目标架构与整改顺序

10.1 不增加新脑袋，收紧边界

这是逻辑目标，不是建议新建一批同名目录或推倒现有包。优先抽无副作用的共享函数和收敛写入口，保留现有有效安全边界。

10.2 按可验收的小批次实施，而不是一次大重构

10.3 工程与签核边界

这轮没有实施任何工作包。后续即使批准“修实现缺陷”，也不等于批准改任务时刻、账户模式、风险参数、模型、技能、SOUL、落盘布局或退役组件。建议每批明确：范围、修复前反例、修复后验收、影响消费者、回滚材料、尚未批准事项。

学习匹配暴露下复发率；纠错谓词执行率；增量消融有消费行为，尚不能证明长期提升
成本同任务同数据下 token、工具耗时、缓存命中、交付质量未测，不报告节省比例

建议先积累连续前瞻观察窗口，再估计稳定性和决策增量。可以采用连续 20 个交易日作为第一轮观测计划，但它只是建议的采样安排，不保证样本已足够证明盈利或统计显著性。真实/模拟零成交必须如实记，不能补造交易提高样本量。

交付与后续决定

最后的判断：系统并不缺更多 Agent 或更多策略，它缺的是把“研究到什么、证据在哪、何时可用、谁允许交易、是否真的成交、究竟学到了什么”连成一条可验证的链。先补这条链，再减重复工程，才是最有价值的重构。
