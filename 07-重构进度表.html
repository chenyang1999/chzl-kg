API vs MCP 选型建议(execute 层持仓/下单该走哪个)

结论:两条腿走路,不是二选一 —— 这是 mcp-api-usage.md 里官方推荐的模式,也符合 CANONICAL “execute 全 Python” 的原则:

层用哪个原因
canghai-execute 的 Python daemon(watcher.py / amygdala.py / 未来的秒级 tick 循环)REST API(8788)daemon 是纯 Python 高频轮询,MCP 协议(JSON-RPC + session handshake + SSE)对一个内部脚本来说是不必要的开销和复杂度;REST 就是 requests.get/post 三行代码,超时/重试/日志都更好控制,和”execute 层不受 LLM/协议层影响”的宪法原则(§1.2 路径 C)更契合
Hermes/Cursor 的 LLM 交互层(research/plan/review 里偶尔要查一下持仓、iLink 提醒里带个仓位快照)MCP(8787)这就是 MCP 存在的意义:Agent 自动选 tool,不用你写 HTTP client 代码

当前的现实阻碍:测试时 REST(8788)端口连接超时,说明 Windows 端目前只起了 MCP 服务,没起 REST 服务。要落地上面的建议,需要:

  1. Windows 端额外跑一次 .\scripts\start_api_qmt.ps1,并设 QMT_SESSION_ID=123457(避免和 MCP 的 123456 冲突,同一账号两个连接会话不能共用 session id)
  2. .env 里补 AGENTQMT_QMT_API_TOKEN / AGENTQMT_QMT_API_PORT(REST 专属,可以和 MCP token 相同)
  3. T2 施工 watcher.py/amygdala.py 时直接用 requests 调 REST,不引入 MCP client 依赖

这个决策不是本次紧急项,T2 开工前(至少还有 1-2 周)落地即可,先记录进这份进度表。
