## 二、① 视觉通道：ARK 实测比 apiyi 慢

### 关键陷阱：ARK 密钥有 scoped key，不是 key 的问题

`providers.volcengine-agent-plan` 的 base_url 是 `https://ark.cn-beijing.volces.com/api/plan/v3`。
早期测试出现 `UnsupportedModel`，一度判断"该端点不支持视觉"——**这是错的**：

```
✅ doubao-seed-2-1-turbo-251015   11.7s → 可用
✅ doubao-seed-2-1-pro-251015     54.9s → 可用
❌ doubao-seed-1-6-250615                → UnsupportedModel
❌ doubao-seed-1-6-flash-250615          → UnsupportedModel
❌ doubao-1-5-vision-pro-250328          → UnsupportedModel
❌ doubao-vision-pro-32k                 → UnsupportedModel
❌ doubao-1-5-vision-lite-250315         → UnsupportedModel
```

`plan/v3` 是 **scoped 端点，只白名单了 2.1 系列**，其它模型一律 `UnsupportedModel`。
所以"换 ARK"实际只有 `doubao-seed-2-1-turbo-251015` 这一个选项可用。

### 单票稳定性：各跑 6 次交错取中位（同一张 147KB PNG、同一个 prompt）

```
  [1] apiyi   26.2s      [1] ARK     68.0s
  [2] apiyi   29.0s      [2] ARK     56.9s
  [3] apiyi   30.7s      [3] ARK    133.2s
  [4] apiyi   30.2s      [4] ARK     28.3s
  [5] apiyi   26.2s      [5] ARK     94.1s
  [6] apiyi   20.2s      [6] ARK     51.9s

  apiyi: 中位 27.6s  最快 20.2s  最慢 30.7s  平均 27.1s
  ARK  : 中位 62.4s  最快 28.3s  最慢 133.2s 平均 72.1s
```

**apiyi 不仅快 2.3x，而且方差小**（20–31s）；ARK 抖动极大（28–133s，5x 波动），
在 concurrency=6 的批量场景下最慢的那一票会拖住整批。

**旁证（另一条独立基准）**：同一张图用更详尽的 prompt（要求输出 trend/pattern/key_levels），
```  # 非交错顺序跑
  apiyi  run1 51.9s → {"trend":"多头","pattern":"筑底回升","key_levels":{"hi20":20.8,"lo20":16.8}}
  apiyi  run2 35.7s → {"trend":"多头","pattern":"双底突破","key_levels":{"hi20":20.7,"lo20":16.8}}
  ARK    run1 311.5s → 同样答案，但耗时 6–9x
  ARK    run2 → APITimeoutError（timeout=200s 都没等到）
```
两条基准结论一致：**ARK 在同 prompt 下慢一个量级，且有硬超时风险**。ARK 未超时那次的
输出与 apiyi 完全一致（hi20=20.8 / lo20=16.8），说明**不是质量问题，纯是延迟问题**。

为何单次探测时 ARK 只要 11.7s？首轮 `ark_models.py` 是顺序冷调，且当时 prompt
更短、`max_tokens=60`。交错跑之后 ARK 的真实排队延迟暴露出来 —— **这正是交错基准的价值**。

### 已落地的改动（默认行为不变）

`src/agents/chart_vision_agent.py`：

- 新增 `_vision_model()`：`VISION_MODEL` > `OPENAI_VISION_MODEL` > `OPENAI_MODEL` > `gpt-4o-mini`
- `_vision_client()` 解析序：`VISION_API_BASE`/`VISION_API_KEY` > `OPENAI_API_BASE`/`OPENAI_API_KEY`
- `analyze_chart_data_only()` 也改用 `_vision_model()`（原来只读 `OPENAI_MODEL`，两处不一致）

**验证默认行为未变**：

```
不设 VISION_* → 模型 seed-2-0-lite-260228, base_url https://api.apiyi.com/v1/
设 VISION_API_BASE=ark.../plan/v3 VISION_MODEL=doubao-seed-2-1-turbo-251015
              → 模型 doubao-seed-2-1-turbo-251015, base_url https://ark.cn-beijing.volces.com/api/plan/v3/
```

> 现在改不改只是一行 `.env`；但**由数据看，不建议切**。

## 三、② mplfinance：单票持平，并发下更慢

### 单票（603598.SH，4 周期，各 3 次）

```
mplfinance       墙钟 ['1.70s','1.12s','1.10s']  中位 1.12s
lwc+playwright   墙钟 ['1.30s','1.15s','1.21s']  中位 1.21s
```

**基本持平** —— 推翻了上一轮"mplfinance 快 9.2x"的基准。那个 9.2x 是拿
`mpf.plot()` 的单周期调用去比 LWC 的四周期 + 数据抓取，**口径不可比**。

### 并发 6（真实快照场景，各 2 轮）

```
第 1 轮  matplotlib(进程内): 6.2s    LWC(subprocess): 2.5s
第 2 轮  matplotlib(进程内): 6.5s    LWC(subprocess): 1.5s
```

**mplfinance 慢 2.5–4x**，根因：`ThreadPoolExecutor` 下 matplotlib 受 **GIL** 约束，
6 个线程串行画图；LWC 是 `subprocess` 跑 Node，6 个进程**真并行**。
用户说"支持批量多并发"——mplfinance 在此架构下恰恰**不是**多并发友好的。

### 已落地的产物（可选、未接线）

`src/analytics/mplfinance_renderer.py`：功能对等移植
- 牛线：`(20·MID + 19·REF(MID,1) + … + 2·REF(MID,18) + REF(MID,20)) / 210`，`MID=(3C+L+O+H)/6`，**跳过 REF(MID,19)**
- 熊线 `MA(牛线,6)`、决策线 `MA(C,50)`、四色四量 5 行 STICKUP、MACD
- 用 `vision_analyze` 逐版视觉验收，修掉三处渲染缺陷：
  1. `volumes` 是**独立列表**（candle 里没有 `volume` 键）→ 成交量一度全 0
  2. 色带压在成交量上 → 副图纵向分区（上方量、下方色带）
  3. 缺时间刻度 → 每格 5 个日期标签

**当前状态**：纯度新增，`grep` 确认 0 处生产引用；默认仍走 LWC。
**价值**：去掉 Node + Playwright 依赖（离线/CI 环境更干净），单票持平，并发不占优。

### 三个具体价值（不是"多给点数据"）

**1. 堵住过度自信。** `600825.SH 新华传媒` 视觉判"偏多，9月30日涨停突破阶段新高"——
但 **RSI=94.9**（极度超买）。视觉能看出"涨得多"，**看不出 RSI 已到 95 这种量化极端**；
而按用户"打板派"口径，RSI 95 + 涨停 = 典型的"要信早信"还是"最后一棒"判据。
这一条直接影响 D1 的竞价动作。

**2. 市值/价位交叉校验，防幻觉价。** `605058.SH 澳弘电子` 视觉给的 price_hint 是
**51.0 / 50.0**，而真实 MA20=41.94、布林上轨 66.31 —— 51 这个数**落在真空区**，
既非均线也非布林轨。历史预案里的幻觉价（旋极信息 17.0 vs 4.14）正是同类问题。
加数值轨后可直接硬校验：`|hint − 任一轨道| > 15%` → 标可疑。

**3. 给量能定性。** 视觉模型完全不汇报量比。而今日：
- `603602.SH 纵横通信` 量比 **5.47**、`301513.SZ 无线传媒` 量比 **5.23** → 显著放量
- `603200.SH 上海洗霸` 量比 **0.47** + MACD 柱转负 → 缩量下跌，视觉却判"偏多"

`603200` 是最典型的：视觉看形态说偏多，数值说缩量 + MACD 转负。**两个信号打架时，
大模型才有真正需要裁决的东西** —— 这正好符合"决策必须大模型做、数值只作输入"的铁律。

### 代价与建议

- 单票 **0.2–0.5s**、12 票 **5.4s**（实测），已是 KB 对账过的可信源（SMA20/SMA50 完全一致）
- 建议：R5 在 chart_vision 之外**并行**取一次 `technical_indicators`，
  以 `numeric_track` 字段与 `chart_vision` **并列**交给 D1，不覆盖、不替代
- 明确**不做**的事：不让数值轨独立产出买卖点（那是纯量价决策，违反铁律）
