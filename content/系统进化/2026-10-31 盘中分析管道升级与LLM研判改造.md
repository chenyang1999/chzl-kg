## 三、逐项真相（可核验硬数据）

### 管道结构

```
Tushare rt_k（4 批）→ run_intraday_snapshot.py → intraday_snapshot_{HHMM}.json（广度+预案现价）
```

### 关键判定修正（均为实测发现，非设计推演）

1. **板块排序不能用涨停绝对数**。普跌日"融资融券 25 只涨停"实为成分 3888 只的宽基噪声（密度 0.0064、中位 -3.07%）；"白酒概念 5 只涨停/48 成分"密度 0.104、中位 +0.46% 才是扩散。改为**涨停密度**排序 + 宽基属性板块按名称剔除（全市场 432 个中剔 16 个）。
2. **"钱在"门槛是涨停 ≥3 只**。芬太尼密度 0.125 排第一但只有 1 只涨停，进结论会误导选股。改为 ⬦ 标注零星、不进结论、不进饼图。
3. **`stop_loss` 不是"现价跌破即失效"**。预案 `exit_rules` 明写"以拟买上沿为基准的引擎风险参考；无当日新仓卖权，不是卖出指令"，且三花智控 stop 35.64 高于昨收 34.50、低于买区 36.79。原实现把 8 只票里 4 只误判成"已失效"。改为按触发价/买区判定（超买区/已触发/买区内/未到价/无预案价），止损只在条件已满足后才谈失效。
4. **"印证"判据不能是 `live_lu >= 1`**。商业航天 T-1 有 11 只涨停、今日只剩 6 只且中位 -4.24%，明显是背离却判成印证。改为按涨停家数保留比例（≥80% 印证 / ≥40% 部分印证 / <40% 背离）+ 相对强度。
5. **"超买区"是背离不是利好**（原映射归到"无响应"）。票走强但预案买点错过 = 追高风险，结论必须写"不追高"。

**两个 LLM job 落点互斥**：增量禁写尾盘定论，尾盘定论禁写分时研判记录。否则 md 会出现两个同名标题，读者无法判断哪段是当轮结论。

**"无数据即退出"守卫**：两 job 都先 `date` 确认日期、检查当日 analysis 文件是否存在；不存在（周末/节假日/数据未落盘）立即停止不写盘，绝不写"今日无数据"占位段落污染文件。

## 四、根因

**为什么原来只有价格表**：方法论一直在 skill 里（`intraday_snapshot_v1` 的"交付物契约"段明确要求结论/板块/梯队/预案对照/三方对照），但**契约写在 skill 里 ≠ 代码实现了它**。`run_intraday_snapshot.py` 只算 market(广度) + pool(现价)，snapshot JSON 里根本没有板块/梯队字段，预案的 `trigger_price`/`buy_zone`/`stop_loss` 在落盘时被丢弃。LLM job 又挂错 skill（`market_scanner_v1`），且从 2026-10-26 起持续 429 失败——分析层实际上从未运行过。

**为什么原来"没有板块"**：不是没数据源，是没接。XTick `/doc/hot/bk` 与 `/doc/hot/board` 一直可用（0.2s 级），项目里也有 `XTICK_TOKEN`，但没人把它们接进盘中管道。

## 五、改进建议

**P0（已完成）**：三段管道接入 cron wrapper + 分析层失败自动降级。

**P1（建议，需签核）**：
1. **补单元测试**：`build_intraday_analysis.py` 的判定逻辑（涨停密度排序、宽基剔除、stop_loss 语义、三方对照比例判据）目前无自动化回归，改动后靠人工比对。建议加 `tests/intraday/test_analysis_judgments.py`，用固定输入快照断言判定结果。
2. **跨源一致性强校验**：本次发现 XTick 全市场（892/4602, n=5577）与 rt_k 返回样本（413/2456, valid_n=2903）口径差异巨大，同一份 md 里两个数并存容易误读。建议渲染时统一标注两者口径，或在 rt_k 有效样本低于 90% 时自动改用 XTick 口径并标降级。
3. **板块成分缓存**：`/doc/hot/bk?symbol=agn` 返回 458 个板块全成分（约 1.1MB），每 10 分钟拉一次浪费 XTick 日配额（限额约 8 万次）。建议按日缓存成分表，只实时取行情。

**P2（可选）**：
4. `xtick_hot_bk` 的 MCP 工具描述（`symbol: all=全市场`）与官方文档（`symbol=agn|sw1|...`）不一致，实际 `all` 报"参数错误"。已在 `docs/13-参考-XTick-API文档.md` 记录官方枚举；可考虑把 MCP server 的描述同步为官方枚举，避免后续 agent 重踩。
