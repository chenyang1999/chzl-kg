## 二、`chart_vision_analyze` 真相（用户第一问）

### 它真在用

今日 `canghai-research` 真实调用 **12 次**，单次 33–44s：

```
08:19:06  chart_vision_analyze completed (37.97s, 2571 chars)
08:19:48  chart_vision_analyze completed (41.29s, 2571 chars)
...
```

输出直接进 `data/research/20260930/R5_stock_profiles.json`：

```json
{"trend": "多头", "pattern": "涨停突破",
 "key_levels": {"hi20": 28.68, "lo20": 24.67, "ma20": 26.25}}
```

→ 流入 `research_summary.json` → D1 预案。**它是 R5"技术形态"维度的唯一真实输入，不是摆设。**

### 但它的旁路快照是废的 ⚠️

存在一套并行机制 `chart_vision_snapshot`（cron `fd61c030d180`，每天 **06:50 + 15:50** 两档），本意是"预生成快照让 R5 读，省掉串行 MCP 调用"。

实测今日：

| 项 | 值 |
|---|---|
| snapshot 覆盖票 | `000938 000977 001339 002396 300017 300223 301308 603893 603986 688018 688521 688766` |
| R5 实际候选 | `000823 002074 002912 300075 301308 600825 601238 603200 603328 603533 603598 605058` |
| **交集** | **1 票**（仅 301308） |

**根因**：`run_chart_vision_snapshot.py` 的 `DEFAULT_UNIVERSE` 是**硬编码的旧票池**（兆易创新/瑞芯微/乐鑫科技/芯原股份…），从不随 R2 龙头更新；cron 调用时也没传 `--universe`。

**双重浪费**：
1. 12 次 vision LLM 调用（每次 33–44s）算的全是**昨日/无关的票**
2. 15:50 那档产物次日 06:50 就被覆盖，**且 R5(08:11) 根本不读它**（当前 R5 skill 对 snapshot 引用 = **0 处**）

→ 每天白烧 **24 次 vision 调用**（两档 × 12 票），产出零价值。

## 七、我的改进建议

### P0 · 建议立刻做

**1. `chart_vision_snapshot` 改造成真正有用，或者关掉**

现状是"每天白烧 24 次 vision 调用，产出 1/12 有用"。两个方向选一：

- **方向 A（推荐）**：把 `DEFAULT_UNIVERSE` 改为**从当日 R2 龙头动态读取**，并把 cron 改成 **只保留 06:50 一档**、15:50 那档删掉。R5 skill 加一句"先读 snapshot，未命中才调 MCP"。**收益**：R5 省 11 次 MCP 调用（约 7–8 分钟），且不再白烧 12 次 vision。
- **方向 B（最省事）**：直接删掉 `fd61c030d180` 这个 cron 和 `run_chart_vision_snapshot.py`。R5 走纯 MCP 直调（现状行为）。**收益**：每天省 24 次 vision 调用，R5 无变化。

**2. cron 失败必须告警**

这次最刺眼的不是 bug，而是**"25 failures in a row" 没有任何人知道**。建议加一个每日巡检：`hermes cron list --all` 里凡 `failure_streak >= 3` 的 job，随早盘简报一起推给用户。已有的 `canghai-health · 每日产出健康检查 (20:30)` 可以承载这个职责。

### P1 · 建议本周做

**3. 建立"配置变更检查清单"（已部分固化）**

这次三个 config 生成器（`setup_hermes_doubao.py` / `register_hermes_mcps.py`）会**把已删的 server 写回去**。本轮已同步修正，但暴露一个模式：**"手改 profile config"和"跑 setup 脚本"会互相打架**。

建议：profile config 的 `mcp_servers` 段标注"由 setup 脚本生成，手改会丢"，或反过来 —— 让 setup 脚本**尊重已有配置**（merge 而非覆盖）。

**4. `research_summary.json` 的生产已修复，但历史欠账**

09-14 ～ 09-29 每天缺失，导致 D1 每天走 `_minimal_summary()` 兜底、`orchestrator_status=degraded`。已建只读脚本 `build_research_summary.py`。建议回填这 12 天，让历史复盘口径一致。

**5. 消除 cron 的"双轨重复"**

现在仍存在结构性重复：

| 功能 | default | profile 级 |
|---|---|---|
| P2 午盘修订 | `35 11 * * 1-5` | `40 11 * * 1-5`（canghai-plan） |
| 笔记站同步 | `30 9` + `18:00` 两个 | —— |
| 竞价校准 | `28 9`（default） | 原 `757e83acebd7`（已删） |

建议**统一原则：一个功能只在一个 profile 里有一个 job**。当前"default 里挂 26 个、profile 里挂 1–2 个"的分布是历史遗留，理解和排障成本都高。

### P2 · 观察项

**6. `tushareMcp` 69 个工具是否还能再砍**

当前白名单偏保守（含大量 `rt_*` 实时接口、`*_vip` 变体）。观察 1–2 周真实调用后再收一轮。

**7. 15:50 snapshot 若保留，是否该改到 16:30 之后**

A 股 15:00 收盘，15:50 跑拿到的是当日完整日 K。如果将来做"收盘后复盘用图表"，这个时点是对的 —— **但现在没有任何消费者**。
